把一份粗粒度的需求文档,拆解、细化为**一组互相独立的需求**,每个需求再拆成**一组互相独立的功能点**,并按统一格式输出中文 Markdown 设计文档。产物的定位是**需求/契约文档**,不是技术实现稿 —— 它要能让前端团队和后端团队各自独立开发。

## 何时使用

- 用户给出一份 `sprint plan` / 客户需求整理 / PRD 片段,要求"拆解""细化""拆成功能点"。
- 用户要为某个需求"出一份开发拆解 + 实施方案文档"。
- 用户认可了某份样板文档,要求"按这个格式继续生成 req2 / req3 …"。

不适用:写具体代码、做技术选型、设计数据库索引/框架细节 —— 那是实现稿,本 skill 刻意不涉及。

## 输入

- 一段粘贴的需求文本,或一个需求文档的路径(如 `sprint9-plan.md`)。
- 可选:用户指定要拆解第几个需求,或一次拆全部。

## 四条核心原则(必须贯彻)

1. **脱离代码实现** —— **不要**写任何特定代码库的内部细节:框架名、类名、注解、ORM/迁移工具、权限框架内部结构、静态元模型等一律不写。**只保留前后端都要对齐的契约**:
   - HTTP 接口(方法 + 路径)
   - 请求体(DTO 名 + JSON 示例 + 字段约束)
   - 响应(JSON 示例)
   - 数据字段(以字段表表达数据模型,而非框架实体)
   - 业务规则、校验、错误码
   - 权限点(以 `资源:动作` 字符串表达,如 `inventory:create`,不展开权限框架实现)
2. **需求独立** —— 每个需求自包含。用一张「范围与边界」表**显式剔除**属于其它需求的内容(只在数据表/表单上预留扩展位),使本需求可被单独开发,不依赖其它需求先完成。
3. **功能独立** —— 每个功能点是一个可独立开发/测试/演示的切片。对前端通常是一个独立 UI/能力(如搜索框、过滤器、状态徽标),对后端是同一端点上可独立叠加的能力。优先按"操作/能力"切分,而不是按表单 Tab 切分(**Tab ≠ 功能点**)。
4. **英译中** —— 输入若为英文(或中英混杂),先翻译成规范中文再拆解;术语、字段名、枚举值、接口路径保持英文原形。

## 流程

1. **读取**输入需求文档/文本。若为英文,先在心里翻译成中文。
2. **识别需求边界**:把文档拆成若干互相独立的需求(需求1、需求2…)。一个需求 = 一个能独立交付的业务能力块。
3. **确认粒度(先展示再落盘)**:先给出"需求清单 + 每个需求的功能点清单(仅标题)"让用户确认粒度,再生成完整文档。除非用户已明确要直接产出。
4. 对**每个需求**,产出一份文档,依次包含:
   - `# 需求N. <模块/能力中文名>(可加英文副名)` + 业务描述段。
   - **范围与边界**表:列出属于其它需求、本需求不实现的内容及其归属(保证需求独立)。
   - **数据模型**:本需求需要的字段表(字段 / 类型 / 约束 / 说明),并注明唯一性等关键规则与权限点。
   - 若干 `## N.x <功能点名>` 小节,**每个自包含**:先一句话描述该功能点,紧跟 `**实施方案**:` 编号步骤(接口、`@RequestBody DTO` + JSON、响应 JSON、业务规则、权限)。
   - 末尾 `## 附录:本需求接口一览` 表格(编号/方法/路径/权限/请求体/响应)。
5. **落盘**:文件名规则见下;与源需求文档同目录(如源在项目根,则产物也在项目根)。
6. 写完后简述本次拆了哪些需求/功能点,并询问是否继续拆下一个需求。

## 输出文档格式规范

**文件命名**:`{模块英文名}-req{N}.md`(模块名 + `req` + 需求号),全小写,如 `inventory-req1.md`、`inventory-req2.md`。

**结构**(严格遵循,参见同目录 `template.md`):

```
# 需求N. <中文名>（<English Name>）
<业务描述:这个需求让谁、做什么、产出什么价值;关键约束>

## 范围与边界（保证需求独立）
<表格:本需求不实现、属于其它需求的内容 → 归属需求>
> 因此本需求接口请求体仅含本需求字段;其它字段由对应需求扩展。

## 数据模型（<表名>）
<字段表:字段 | 类型 | 约束 | 说明>
**唯一性规则**:...
**权限点**:`资源:read/create/edit/delete` ...;写操作记审计。

## N.1 <功能点名>
<一句话功能描述>
**实施方案**：
1. 创建一个接口 `METHOD /path`,需要 `资源:动作` 权限。
   `@RequestBody XxxRequest`
   ```jsonc
   { "field": "value"  // 约束:必填/可空/长度/枚举 }
   ```
2. <校验/业务规则,引用其它功能点编号>
3. ...
N. 返回响应数据 `XxxResponse`(或"响应数据 **无**"):
   ```jsonc
   { ... }
   ```

## N.2 ...
（同上,每个功能点自包含)

## 附录:本需求接口一览
<表格:编号 | 方法 | 路径 | 权限 | 请求体 | 响应>
```

**写法要点**:
- 请求体/响应一律给**带注释的 JSON 示例**(`jsonc`),注释标注必填/可空/长度/枚举/唯一等约束。
- 功能点之间用编号互相引用(如"校验见 1.2""结构见 1.3"),避免重复大段内容。
- 跨模块联动(如复用别的模块的下拉数据接口、需要给某接口加权限)用 `>` 引用块单独点出,方便前后端注意。
- 数量/状态等"只读、由其它操作变更"的字段,明确标注只读及其变更来源。

## 质量检查清单(落盘前自检)

- [ ] 输入是英文的话,已全部翻译为规范中文(术语/字段/路径保留英文)。
- [ ] 没有出现任何特定代码库的框架/类名/注解/ORM/权限框架内部细节。
- [ ] 每个需求有「范围与边界」表,明确剔除了属于其它需求的内容。
- [ ] 每个功能点自包含:描述紧跟自己的实施方案,没有把"功能清单"和"实施方案"拆成两大块。
- [ ] 每个写接口都给了 `@RequestBody` DTO + JSON;每个接口都给了响应(或注明无)。
- [ ] 文件名符合 `{模块}-req{N}.md`。
- [ ] 末尾有接口一览附录。
