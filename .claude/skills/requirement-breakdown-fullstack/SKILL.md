把一份粗粒度的需求文档,拆解、细化为**一组互相独立的需求**,每个需求再拆成**一组互相独立的功能点**,并按统一格式输出中文 Markdown 设计文档。产物的定位是**需求/契约文档**,不是技术实现稿 —— 它要能让前端团队和后端团队各自独立开发。

本 skill 是 `requirement-breakdown` 的**前后端一体版**:对每个需求同时给出两侧契约,并保持二者对称(都脱离各自的实现细节)。

- **后端契约** —— 接口、请求/响应 JSON、数据字段、业务规则、权限点(脱离框架/类名/ORM)。
- **前端界面/交互契约** —— 页面清单、低保真 ASCII 线框、功能点↔控件映射、交互状态(脱离设计系统色值/token/组件库)。

## 何时使用

- 用户要"拆解/细化需求",并且**要带界面/页面线框/交互**,出一份前后端一体的设计文档。
- 用户认可了某份前后端一体样板,要求"按这个格式继续生成 req2 / req3 …"。
- 仅要后端契约(不需要界面线框)时,改用 `requirement-breakdown`,不要用本 skill。

不适用:写具体代码、做技术选型、出像素级视觉稿(配色/token/间距) —— 那是实现稿/视觉稿,本 skill 刻意不涉及。

## 输入

- 一段粘贴的需求文本,或一个需求文档的路径(如 `sprint9-plan.md`)。
- 可选:用户指定要拆解第几个需求,或一次拆全部。

## 五条核心原则(必须贯彻)

1. **后端脱离代码实现** —— **不要**写任何特定代码库的内部细节:框架名、类名、注解、ORM/迁移工具、权限框架内部结构、静态元模型等一律不写。**只保留前后端都要对齐的契约**:
   - HTTP 接口(方法 + 路径)
   - 请求体(DTO 名 + JSON 示例 + 字段约束)
   - 响应(JSON 示例)
   - 数据字段(以字段表表达数据模型,而非框架实体)
   - 业务规则、校验、错误码
   - 权限点(以 `资源:动作` 字符串表达,如 `inventory:create`,不展开权限框架实现)
2. **前端脱离设计系统(与原则1对称)** —— 前端契约只描述**界面结构与交互**,**不要**写任何具体设计系统的内部细节:色值/设计 token(如 `primary-300`、`surface-2`)、渐变名、组件库名、间距/字号数值、品牌主题一律不写——它们等价于后端侧的框架/类名,会把需求文档耦合到某个设计系统。**只保留前后端都要对齐的界面契约**:
   - 页面清单(本需求有哪些页面 / 抽屉 / 弹窗,各含哪些功能点)
   - 低保真 ASCII 线框(只画布局与信息层级,用箭头标注每块对应的功能点编号)
   - 功能点 ↔ UI 控件映射、字段 ↔ 控件类型(输入框 / 下拉 / 日期 / 上传 / 徽标)
   - 交互状态(空态、loading、置灰条件、倒计时、错误提示落在哪个控件、状态流转)
   > 视觉稿(配色、token、间距)是另一份独立交付物,本 skill 刻意不涉及;仅当用户在某需求上**明确要求**时另行追加。
3. **需求独立** —— 每个需求自包含。用一张「范围与边界」表**显式剔除**属于其它需求的内容(只在数据表/表单上预留扩展位),使本需求可被单独开发,不依赖其它需求先完成。
4. **功能独立** —— 每个功能点是一个可独立开发/测试/演示的切片。对前端通常是一个独立 UI/能力(如搜索框、过滤器、状态徽标),对后端是同一端点上可独立叠加的能力。优先按"操作/能力"切分,而不是按表单 Tab 切分(**Tab ≠ 功能点**)。每个功能点既落到后端契约,也落到界面线框的某个控件。
5. **英译中** —— 输入若为英文(或中英混杂),先翻译成规范中文再拆解;术语、字段名、枚举值、接口路径保持英文原形。

## 流程

1. **读取**输入需求文档/文本。若为英文,先在心里翻译成中文。
2. **识别需求边界**:把文档拆成若干互相独立的需求(需求1、需求2…)。一个需求 = 一个能独立交付的业务能力块。
3. **确认粒度(先展示再落盘)**:先给出"需求清单 + 每个需求的功能点清单(仅标题)"让用户确认粒度,再生成完整文档。除非用户已明确要直接产出。
4. 对**每个需求**,产出一份文档,依次包含:
   - `# 需求N. <模块/能力中文名>(可加英文副名)` + 业务描述段。
   - **范围与边界**表:列出属于其它需求、本需求不实现的内容及其归属(保证需求独立)。
   - **数据模型**:本需求需要的字段表(字段 / 类型 / 约束 / 说明),并注明唯一性等关键规则与权限点。
   - **界面与交互契约(前端)**:页面清单表 + 每个页面一张低保真 ASCII 线框(用箭头标功能点编号)+ 控件映射 + 交互状态清单。放在数据模型之后、功能点之前,让前端先拿到整体界面骨架。
   - 若干 `## N.x <功能点名>` 小节,**每个自包含**:先一句话描述该功能点,紧跟 `**实施方案**:` 编号步骤(接口、`@RequestBody DTO` + JSON、响应 JSON、业务规则、权限),末尾加一行 `**界面落点**:` 把该功能点钉到某页面的某控件及其交互状态。
   - 末尾 `## 附录:本需求接口一览` 表格(编号/方法/路径/权限/请求体/响应)。
5. **落盘**:文件名规则见下;与源需求文档同目录(如源在项目根,则产物也在项目根)。
6. 写完后简述本次拆了哪些需求/功能点,并询问是否继续拆下一个需求。

## 输出文档格式规范

**文件命名**:`{模块英文名}-req{N}.md`(模块名 + `req` + 需求号),全小写,如 `inventory-req1.md`、`inventory-req2.md`。

**结构**(严格遵循,参见同目录 `template.md`):

```
# 需求N. <中文名>（<English Name>）
<业务描述:这个需求让谁、做什么、产出什么价值;关键约束>

## 范围与边界（保证需求独立）
<表格:本需求不实现、属于其它需求的内容 → 归属需求>
> 因此本需求接口请求体仅含本需求字段;其它字段由对应需求扩展。

## 数据模型（<表名>）
<字段表:字段 | 类型 | 约束 | 说明>
**唯一性规则**:...
**权限点**:`资源:read/create/edit/delete` ...;写操作记审计。

## 界面与交互契约（前端）
**页面清单**:<表格:页面/抽屉/弹窗 | 类型 | 包含功能点>

**<页面名> 线框**:
\```
┌──────── <页面标题> ────────┐
│ [搜索______] [+ 新建]       │  ← N.2 列表/搜索
│ ┌ 名称 ── 状态 ── 操作 ──┐ │
│ │ 紧急    启用   [删除]   │ │  ← 行内 N.1/N.3
│ └────────────────────────┘ │
└────────────────────────────┘
\```
> 只画布局与信息层级;**不写**色值/token/组件库名。每块用 `←` 标注对应功能点编号。

**控件映射**:<表格:UI 控件 | 类型 | 绑定字段 | 关联功能点>
**交互状态**:空态 / loading / 置灰条件 / 倒计时 / 错误提示落点 / 状态流转。

## N.1 <功能点名>
<一句话功能描述>
**实施方案**：
1. 创建一个接口 `METHOD /path`,需要 `资源:动作` 权限。
   `@RequestBody XxxRequest`
   ```jsonc
   { "field": "value"  // 约束:必填/可空/长度/枚举 }
   ```
2. <校验/业务规则,引用其它功能点编号>
3. ...
N. 返回响应数据 `XxxResponse`(或"响应数据 **无**"):
   ```jsonc
   { ... }
   ```
**界面落点**:<页面名> 的 <控件>;<交互状态,如"提交失败时输入框下红字定位到 field">。

## N.2 ...
（同上,每个功能点自包含,均含「界面落点」一行)

## 附录:本需求接口一览
<表格:编号 | 方法 | 路径 | 权限 | 请求体 | 响应>
```

**写法要点**:
- 请求体/响应一律给**带注释的 JSON 示例**(`jsonc`),注释标注必填/可空/长度/枚举/唯一等约束。
- 功能点之间用编号互相引用(如"校验见 1.2""结构见 1.3"),避免重复大段内容。
- 跨模块联动(如复用别的模块的下拉数据接口、需要给某接口加权限)用 `>` 引用块单独点出,方便前后端注意。
- 数量/状态等"只读、由其它操作变更"的字段,明确标注只读及其变更来源。
- **线框只画一次**:一张线框对应一个页面,上面可承载多个功能点(用 `←` 标编号);不要为每个功能点重画整页。功能点小节里用「界面落点」一行指回线框上的控件即可。
- **线框保持低保真**:用纯 ASCII 框线表达布局与层级,够前端理解信息架构即可;**禁止**写 `primary-300`/`surface-2`/渐变名/具体色值/组件库名——那是视觉稿的事。

## 质量检查清单(落盘前自检)

后端契约:
- [ ] 输入是英文的话,已全部翻译为规范中文(术语/字段/路径保留英文)。
- [ ] 没有出现任何特定代码库的框架/类名/注解/ORM/权限框架内部细节。
- [ ] 每个需求有「范围与边界」表,明确剔除了属于其它需求的内容。
- [ ] 每个功能点自包含:描述紧跟自己的实施方案,没有把"功能清单"和"实施方案"拆成两大块。
- [ ] 每个写接口都给了 `@RequestBody` DTO + JSON;每个接口都给了响应(或注明无)。

前端契约:
- [ ] 有「界面与交互契约」小节:页面清单 + 每页一张 ASCII 线框 + 交互状态。
- [ ] 线框只画布局/层级,**没有**任何色值/token/渐变/组件库名(违反则等同后端写了类名)。
- [ ] 线框上每块都用 `←` 标了对应功能点编号;每个功能点小节都有「界面落点」一行。
- [ ] 列表/表单类功能点给了控件类型与字段绑定;关键交互状态(空态/loading/置灰/倒计时/错误落点)已列出。

通用:
- [ ] 文件名符合 `{模块}-req{N}.md`。
- [ ] 末尾有接口一览附录。
